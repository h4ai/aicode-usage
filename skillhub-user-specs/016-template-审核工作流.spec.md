# 模板审核工作流

## 1. 需求背景
- 目标：提供给管理员和平台治理者一种统一、标准的机制，确保内部发布的“项目初始化模板”满足安全和工程规范。
- 成功标准：任何带有脚手架代码及配置的项目模板，发布后需经过预设的自动扫描和/或人工审批才能成为全员可见的 `PUBLISHED` 状态。
- 范围边界：包含对上传 ZIP 及拉取的 Git 仓库资源的扫描和审批操作；基于已有的审核工作流（参考 SPEC-005）做能力扩展，但不支持实时代码在线修改。

## 2. 需求描述
- 功能概述：一个让模板创建、更新后必须经过的一套包含自动检查（如安全扫描、依赖检查）和人工管理员审核状态流转的系统功能。
- 业务价值：保障企业内部工程资产的安全性与合规性，拦截包含敏感信息（凭证硬编码、恶意后门脚本等）的劣质模板，控制发布节奏。
- 核心场景：架构师提交了一个新版 `@backend-team/java-springboot`，包含了一些公司内部镜像源和配置。提交后状态变为 `PENDING_REVIEW`，系统扫描无安全风险后，自动转由对应命名空间或全局管理员进行批准或驳回。

## 3. 用户旅程
- 主要用户：管理员、平台审核人员、架构师/模板作者
- 主路径：
  1. 架构师在 Web/CLI 提交 `template publish`。
  2. 模板状态自动置为 `PENDING_REVIEW`，进入审核队列。
  3. 自动扫描机制（可选的插件/Webhook）触发，例如检查 ZIP 或仓库是否存在硬编码的 Secret。
  4. 扫描通过后，管理员收到审核通知。
  5. 管理员在后台“审核管理”页面查看模板的 `manifest` 变更、依赖 Skill 及文件结构摘要。
  6. 管理员点击“通过(Approve)”，模板状态变更为 `PUBLISHED`，系统发送通知给作者。
- 异常路径：
  1. 自动扫描发现安全风险 → 模板被拦截并置为 `REJECTED`，通知作者修改后重新提交。
  2. 管理员发现描述不清或不合规 → 点击“驳回(Reject)”，并必须填写驳回原因（如“依赖了未经验证的旧版 Skill”），通知作者。
  3. 作者在审核期间发现错误，主动撤回 → 状态变更为 `DRAFT` 或中止此次发布版本。
  4. 审核超时 → 根据策略可选是否发出提醒通知或自动驳回。

## 4. 页面结构
- 页面布局：管理后台新增“模板审核”Tab，分栏展示列表与详情（右侧弹出/新页）。
- 关键区域：
  - 待审核列表：展示申请时间、申请人、Namespace、模板名及版本、当前状态。
  - 审核详情视图：包含基础信息、本次提交的文件摘要/Diff、包含的 Skill 依赖清单。
  - 审核操作区：Approve、Reject 按钮，以及填写 Reject 理由的输入框。
- 状态流转：PENDING_REVIEW -> (扫描失败/人工驳回) REJECTED | (审批通过) PUBLISHED | (过期/撤回) DRAFT

## 5. 输入输出

### 5.1 输入
| 场景 | 输入 | 说明 |
|------|------|------|
| 自动扫描 | webhook / 脚本返回结果 | 安全插件或服务检测后的状态（Pass/Fail）及日志 |
| 管理员审批 | 点击按钮及可能填写的理由 | 审批人做出“通过”或“驳回”的判断并提交 |
| 作者撤回申请 | 点击操作 | 在审核中状态下，用户主动作废此次提交 |

### 5.2 输出
| 场景 | 输出 | 说明 |
|------|------|------|
| 审核结果 | 状态扭转为 PUBLISHED / REJECTED | 系统内模板的状态改变，决定其是否可被搜索和 init |
| 审核通知 | 系统消息 / 飞书/企微通知 | 告知申请人审核已通过，或列明被驳回的详细原因 |
| 扫描报告 | 检查日志 | 如果由于安全扫描失败，提供详细的不合规说明（如“发现敏感词”）供修改参考 |

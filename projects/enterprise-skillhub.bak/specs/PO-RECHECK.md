# PO Recheck — SPEC-001 ~ SPEC-005（产品视角）

> 审核人: PO Agent
> 审核时间: 2026-03-19

## 一、用户场景完整性检查
1. **SPEC-001 (认证)**: 覆盖了登录、登出、获取信息。遗漏场景：AD密码过期或必须修改时的提示；JWT 12h 过期后正在操作页面的无缝重新登录/状态保存体验。
2. **SPEC-002 (数据模型 & CRUD)**: 核心 CRUD 和列表可见性已覆盖。遗漏场景：Skill Owner 转移（如换组或离职时转给同事）；用户点赞/收藏 (Star) 操作的具体 API 描述不全；评论 (Comment) 功能的模型有了，但没有相关接口。
3. **SPEC-003 (版本 & 文件)**: 发布、下载、历史版本已覆盖。遗漏场景：取消发布/撤回有重大Bug的版本；旧版本的自动清理策略。
4. **SPEC-004 (搜索)**: 语义和关键字搜索已覆盖。遗漏场景：基于热门/下载量排名的默认推荐列表接口。
5. **SPEC-005 (审核)**: 自动和人工审核流程基本完备。遗漏场景：审核退回后发布者的修改流向；审核员请假或离职时的重新分配机制。

## 二、业务规则合理性
1. **可见性三级控制 (PUBLIC/DEPARTMENT/PRIVATE)**:
   - *合理性*: 基本覆盖企业场景。
   - *建议*: DEPARTMENT 只支持按部门名称过滤可能会有问题（名称变更），建议支持 AD 的 Department ID/DN 或者允许挂载多个指定用户（即白名单模式）。
2. **审核流程对发布者的友好度**:
   - *合理性*: 目前 `REJECTED` 和 `REVISION_REQUESTED` 状态区分了。
   - *建议*: 对于退回修改（REVISION_REQUESTED），发布者如果只是改个错别字还需要重新打 Tag 提一个全新 Version 会很繁琐。建议允许在当前未 APPROVED 的 version 上直接覆盖上传重新触发自动审核。
3. **12h JWT 无 Refresh Token 的影响**:
   - *影响*: 12 小时够一天工作时间，但在第二天早上如果用户在写较长评论或表单时突然 token 失效，会丢失数据。
   - *建议*: 若不引入 Refresh Token，前端必须做好全局 401 拦截并缓存未提交表单状态。

## 三、验收标准补充建议
1. **SPEC-001**: 增加 "用户 JWT Token 到期时，前端触发 401 后能友好提示并保留当前用户的输入内容"。
2. **SPEC-002**: 增加 "管理员(ADMIN) 能够强制转移某 Skill 的 ownerId"。增加 "评论创建与展示的正常运作"（若决定做评论）。
3. **SPEC-003**: 增加 "版本处于 PENDING_REVIEW 或 APPROVED 状态时，如果发现高危安全漏洞，ADMIN 能够紧急将其状态设为 ARCHIVED 或强制下架"。
4. **SPEC-004**: 增加 "当用户连续输入相同 query 时搜索结果防抖且性能正常"。
5. **SPEC-005**: 增加 "如果审核单超时 48 小时且审核员为离职/禁用状态，系统能自动将单子转回 PENDING_MANUAL 以便重新分配"。

## 四、前端交互完整性
- **SPEC-001**: 足够，但需明确 401 拦截后的保存页面状态交互。
- **SPEC-002**: 缺少关于 Owner 转移和 Comment 评论区的交互描述。
- **SPEC-003**: 缺少对于用户由于下载权限问题导致的 403 页面展现说明。
- **SPEC-004**: 搜索组件交互基本足够。
- **SPEC-005**: 缺少“转派给其他审核员”的具体交互UI，及审核通知在工作台的消息红点。

## 五、边界情况补充
- **新员工入职（AD 新增用户）的首次登录**: 应当能够自动静默初始化 `User` 表记录，无需额外审批；系统提供默认的新手引导 (Onboarding)。
- **员工离职（AD 禁用用户）后的权限回收**: 虽然其 JWT 会在 12h 内失效，但如果 AD 禁用后马上需要强制踢出，则需后端在每次请求关键接口时验证 AD 状态，或者至少有个全局的黑名单/被禁用标志位缓存拦截。建议在 SPEC-001 补充每日同步或登录时同步的离职账号打 `DISABLED` 标签。
- **Skill 作者离职后，Skill 的归属和管理**: 离职后 Owner 为 `DISABLED`。建议增加一个认领流程，或由 ADMIN 批量划转给该员工的主管。
- **审核员全部请假时的审核流程**: `PENDING_MANUAL` 任务堆积。系统需要支持 ADMIN 一键配置“降级策略”（如非高危类自动通过，或临时赋予另外组审批权限）。

## 六、整体评价
**PASS_WITH_COMMENTS**

整体模型和业务逻辑闭环已经打通，核心痛点都已解决。但从产品体验和企业级边界处理上（如离职人员资产交接、401 体验、快捷重新提审）仍有遗漏。可进入开发阶段，但请开发在设计接口时预留上述建议的扩展性，后续在迭代中通过新的 User Story 补齐。

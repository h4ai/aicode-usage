### 关键 Bug 修复：@Public 路由下 JWT 可选解析
- **问题**：`@Public()` 装饰器让 `JwtAuthGuard.canActivate` 直接 return true，跳过 JWT 解析 → `req.user` 永远 undefined → 部门可见性对所有人返回 403
- **根因**：即使带了有效 Bearer token，Public 路由也不解析 JWT
- **修复**：改造 `canActivate`，isPublic 时尝试解析 JWT（catch 错误不抛出），Observable 返回值用 `firstValueFrom` 转换
- **TS 编译问题**：`super.canActivate()` 返回 `boolean | Promise<boolean> | Observable<boolean>`，需要用 `isObservable()` + `firstValueFrom()` 处理
- **Commit**: `b2db472` (fix: parse JWT on @Public routes for optional auth)

## Dev 工作流系统性修复（18:20-18:38）

### 根因分析
Monitor 18:02 报告的 7 个违规（TASK-003A 坏 JSON, TASK-002/009 非标准 regression_check, 4 个小写 status）**全部是同一个根因**：

TASK-011 Dev subagent 合并 5 个 worktree 分支时用 "accept task branch version" 策略解决 TASK JSON 冲突，把 PM 在 main 上的修复（cc2d01b）全部覆盖回 Dev subagent 的旧值。

**核心问题**: TASK JSON 有两个写入者（PM + Dev），merge 策略没有区分代码文件和数据文件。

### 三层系统性修复（commit `579e339`）

**第一层：写时防御 — `update-task.js`（新建）**
- 6KB 脚本，替代直接 jq/编辑器修改 TASK JSON
- 自动 status 大写、regression_check 规范化
- 内置状态机（阻止 PENDING→DONE 等非法转换）
- event_log 自动追加
- JSON 写前 roundtrip 校验
- 用法: `node update-task.js TASK-XXX --status REVIEW --regression-check pass --add-commit abc123`

**第二层：合并时修复 — `worktree-manage.sh` post-merge hook**
- merge 后自动修复 broken JSON（尾部逗号等）
- 自动规范化 status 大小写
- 自动规范化 regression_check 值
- 运行 validate-task.js 做最终校验

**第三层：规范约束 — AGENT-SOP Phase 5 更新**
- 强制要求所有 TASK JSON 修改通过 update-task.js
- 禁止直接 jq/编辑器修改

### 四层防御体系总结
```
写入时 → update-task.js（状态机 + 规范化）
合并时 → post-merge hook（自动修正）
巡检时 → monitor-check.js v2（11 项检查 + 趋势分析）
派发前 → validate-task.js（30+ 条规则）
```

### Git
- commit `cc2d01b`: monitor-check 初次改进
- commit `42991f8`: monitor-check v2 完整升级

### 关键教训
- **数据文件和代码文件的 merge 策略应该不同** — 代码可以 "accept theirs"，但状态数据文件应该 "accept ours"（main 优先）或做字段级合并
- **写入端不做校验 = 读取端永远在修 bug** — 必须在源头（update-task.js）做规范化
- **Dev subagent 不知道 PM 在 main 上改了什么** — worktree 分支创建后 main 的变更对分支不可见，需要 post-merge 补偿

## ClawTeam 框架深度分析（22:59-23:10）

### 沈老板要求分析 https://github.com/HKUDS/ClawTeam

### ClawTeam 核心机制（源码级分析）
1. **Mailbox 通信**: 文件系统/ZeroMQ 消息邮箱，每个 Agent 独立 inbox，支持 send/broadcast/peek
2. **TaskStore**: 文件级任务管理 + fcntl 文件锁 + blocked_by 依赖自动解锁
3. **Spawn Registry**: PID/tmux 进程注册 + is_agent_alive() 死亡检测 + 自动释放锁
4. **Git Worktree + tmux**: 每个 Agent 独立 worktree + tmux window，`board attach` 实时监控

### 我们的 7 大独有优势（vs ClawTeam）
1. **四道门禁质量防线** — ClawTeam 没有任何验收机制
2. **Monitor 合规巡检** — 11 项检查 + 告警趋势 + 历史追踪（ClawTeam 只统计数量）
3. **TASK JSON SSOT** — 30+ 字段结构化档案 vs ClawTeam 12 字段便签
4. **5 角色专业分工** — PM/Dev/QA/PO/Monitor vs Leader/Worker 二层
5. **经验学习 + 知识沉淀** — .learnings + Pattern-Key + auto-promote（ClawTeam 零）
6. **Spec 驱动开发（SDD）** — SPEC→Matrix→Checklist→Report→Acceptance（ClawTeam 零）
7. **TDD 强制 + 回归保护** — Red/Green/Refactor + regression_check（ClawTeam 零）

### ClawTeam 可借鉴的改进
- **P0**: 死亡检测 + 自动回收（pm-heartbeat.js 加 subagent 健康检查）
- **P1**: 任务依赖自动解锁（update-task.js --status DONE 时 resolve dependents）
- **P1**: 文件级邮箱（shared/inbox/ 目录 + heartbeat 读取，绕过 agentToAgent 限制）
- **P2**: 任务耗时统计（started_at/duration_seconds）
- **P2**: tmux Dashboard（实时观察 Agent 输出）

### 核心结论
> ClawTeam 在「协作基础设施」上更强，我们在「工程质量保障」上远远领先。最佳策略是取 ClawTeam 的基础设施，叠加我们的质量体系。两者互补，不是替代。
